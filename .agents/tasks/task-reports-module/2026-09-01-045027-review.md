# Reports module with individual-student authorization gating

The change extracts the existing inline reports tab from `AdminClient.tsx` into a dedicated `ReportsClient.tsx` component and expands it from two basic tables into a 7-tab reports module: Dashboard, Por Usuario, Por Área, Por Grupo, Por Fecha, Por Carrera, and Por Método. Alongside the reports work, the diff also ships a new `PENDING_AUTHORIZATION` lifecycle state for sessions submitted by individually-authenticated students (no cohort code), blocking those students from seeing their results until an admin transitions the session to a reviewed status. The read-access guard in `read-access.ts` enforces this gate server-side.

Watch for: (1) **confirmed** — `AUTHORIZED` is declared as a `ReviewStatusCode` and tested in read-access, but no admin UI surfaces sessions in `PENDING_AUTHORIZATION` state as a queue, leaving no discoverable path for staff to act on them. (2) **confirmed** — the `pendingAuth` confirmation card in `AssessmentClient` renders below the submit button, which remains visible and re-clickable after the session is saved, risking duplicate session creation. (3) **confirmed** — `AreaTab` splits `dominantCode` character by character; for TIPOV, CIPR, and MAGDALENA where codes are not single-letter-per-dimension alphabets, this produces meaningless character bins. (4) **confirmed** — mixed-method aggregation in the "All methods" view mislabels CHASIDE letters using RIASEC label names.

**Verdict**: NEEDS_CHANGES

---

## High-level view

`ReportsClient` is a pure client-side aggregation component receiving the same `sessions` and `cohorts` props already loaded by `AdminClient`. All 7 sub-tabs compute their data via `useMemo` from those props, so no new API calls are introduced. The data is stale from page load; the existing "Última actualización" banner makes this transparent to the admin.

The `PENDING_AUTHORIZATION` state extends the existing review status enum and plugs into the existing dictamen dialog for staff. The sessions route sets this status automatically when a non-staff, non-cohort-code authenticated user submits. The read-access guard blocks those students server-side until the status changes. The gap is that there is no dedicated admin workflow to find and act on the pending-authorization queue: an admin must know to open the dictamen dialog and manually set the status to `AUTHORIZED` or another value.

`AreaTab` uses dominant-code character splitting to count area frequencies. For RIASEC and CHASIDE this maps cleanly to their letter-per-dimension semantics. For TIPOV, CIPR, and MAGDALENA dominant codes are arbitrary strings and the split produces confusing single-character counts. When the "All methods" filter is active, CHASIDE letters are resolved first against `RIASEC_LABELS`, so `C` (Ciencias Biológicas in CHASIDE) is labeled "Convencional" (its RIASEC meaning).

## `PENDING_AUTHORIZATION` state machine and the missing queue

The sessions route determines `isIndividualStudent` as `!body.cohortCode && currentUser !== null && !isStaffRole(currentUser.role)`. The branching covers the three stated cases correctly. The read-access guard blocks on `reviewStatus === "PENDING_AUTHORIZATION"` before reaching the owner-email check.

The functional gap is on the admin side. `REVIEW_STATUS_CODES` now includes `PENDING_AUTHORIZATION` and `AUTHORIZED`, so both appear in the dictamen dialog status dropdown. An admin can open the dictamen dialog to change the status. But there is no filtered view, no count badge, and no dedicated action that surfaces the authorization backlog. An admin who doesn't know to look for this status will miss it.

The `pendingAuth` card in `AssessmentClient` renders unconditionally after the submit `</div>`. After `requiresAuthorization` returns true, `setSubmitting(false)` re-enables the button and the card appears at the bottom of the DOM. A second submit creates a new session with a different UUID pointing to the same student, producing a duplicate that the student cannot see but staff will encounter in the evaluaciones table.

## Area frequency counting for non-RIASEC methods

`AreaTab` iterates over `s.dominantCode.split("")` and increments a frequency map for each character. For RIASEC (`"RIA"`) and CHASIDE (`"HAS"`) this maps each character to a dimension label via `RIASEC_LABELS` and `CHASIDE_LABELS`. When `areaMethodFilter` is `"TIPOV"`, `"CIPR"`, or `"MAGDALENA"`, dominant codes are not defined as single-letter-per-dimension alphabets, so `getAreaLabel` returns the raw character with no label and the chart bins mean nothing. The fix is to tally whole dominant codes for those three methods.

## `AreaTab` label resolution with mixed-method data

When `areaMethodFilter === "ALL"`, `getAreaLabel` checks `RIASEC_LABELS[letter]` first. Letters `C` and `A` exist in both alphabets with different meanings: RIASEC `C` = Convencional, CHASIDE `C` = Ciencias Biológicas; RIASEC `A` = Artístico, CHASIDE `A` = Arte (similar enough to be harmless, but `C` is clearly wrong). Any CHASIDE session's `C` contribution ends up tallied under "Convencional" in the all-methods chart.

## Test coverage

Three new tests in `read-access.test.ts` (cases 7, 8, 9) cover the anonymous-cohort bypass, `PENDING_AUTHORIZATION` block, and `AUTHORIZED` pass. Not tested: the `POST /api/sessions` route logic that sets `reviewStatus` based on `isIndividualStudent`, and the `AssessmentClient` branch that sets `pendingAuth` from `requiresAuthorization`. The route is the only place that decides which status a session gets, and a regression there would be silent.
