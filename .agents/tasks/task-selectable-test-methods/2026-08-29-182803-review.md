# Selectable vocational test methods: v1 review fixes for Tutor IA, CHASIDE Interés/Aptitud, and scale captions (v2)

The fix commit (`819caaf`) addresses the three confirmed issues from the v1 review without touching the RIASEC engine, its tests, or the authorization path. The Tutor IA chat route now branches on `session.methodId`: RIASEC keeps its real score/career context while CHASIDE/TIPOV ground the prompt on the persisted `method_scores` (dominant areas, per-dimension values, interpretation) via a new `TutorMethodContext` and a method-aware early-return in `buildTutorSystemPrompt`. The CHASIDE results panel renders per-area Interés (max 10) and Aptitud (max 4) separately from `method_scores.raw`, with `StoredMethodScores.raw` persisted by the sessions API and read back defensively (old rows → `raw:null` → Spanish notice). The non-RIASEC scale endpoint captions in `AssessmentClient` now follow button order.

**Watch for:** nothing blocking. All three fixes are verified against the code and locked by new tests — `tutor-prompt.test.ts` asserts a zero RIASEC vector cannot leak into a non-RIASEC prompt; `chaside-engine.test.ts` asserts the `raw.interes`/`raw.aptitud` count maps survive JSON round-trip (confirmed). The RIASEC engine, `engine.test.ts`, seed, and `authorizeSessionRead` gating are unchanged (confirmed).

**Verdict**: APPROVED

## High-level view

For non-RIASEC sessions the chat route sets `ctx.method` and never populates `ctx.scores`/`ctx.dominantCode`; `buildTutorSystemPrompt` handles `ctx.method` with an early return before the RIASEC block. The "Código RIASEC Dominante" line and the zero-profile score list are gated behind `if (ctx.dominantCode && ctx.scores)`, which the non-RIASEC path never reaches — so no zero RIASEC profile or RIASEC career matches leak into a CHASIDE/TIPOV conversation.

The CHASIDE Interés/Aptitud split is coherent end to end: the engine emits `raw: { interes, aptitud, ... }` count maps, the sessions API persists `result.raw`, `parseMethodScores` reads it back only when it is a non-array object (else `null`), and the results page validates the same shape before dividing by the documented maxima (10 and 4). Old or malformed rows degrade to a Spanish notice instead of the previous misleading combined bars.

Fix #3 is a one-line caption swap so the low/high legend matches button render order; RIASEC captions are untouched.

No regression surface was introduced: the RIASEC chat branch is behavior-equivalent to before, persistence stays additive and backward-compatible, authorization runs before any method branching for chat/report/results, and the fix adds no import-time DB/network, preserving the no-env build invariant.

### Tutor IA now grounds on the real method result

The chat route splits on `session.methodId` after `authorizeSessionRead` succeeds. The non-RIASEC path builds `ctx.method` from `session.methodScores` and never sets `ctx.scores` or `ctx.topCareers`, so the RIASEC career matcher is not invoked against the all-zero vector that non-RIASEC sessions store in the r..c columns:

```ts
} else {
  const ms = session.methodScores;
  ctx.method = {
    methodId: session.methodId,
    methodName: getMethod(session.methodId).name,
    dominantCode: session.dominantCode || null,
    dominantSummary: ms?.interpretation ? null : session.dominantSummary,
    interpretation: ms?.interpretation ?? null,
    dimensionScores: ms?.dimensionScores?.map((d) => ({ code, title, value })),
    studentName: session.studentName,
  };
}
```

`buildTutorSystemPrompt` mirrors the split: when `ctx.method` is present it appends only method-derived lines (dominant dimensions, top-6 per-dimension values sorted desc, interpretation, optional knowledge block) and returns before any RIASEC text. The `Código RIASEC Dominante` line and `scoresLines(ctx.scores)` sit inside the later `if (ctx.dominantCode && ctx.scores)` block the method path cannot reach. `getMethod(session.methodId)` cannot throw because `loadSession`/`normalizeMethodId` guarantee `methodId` is always a registered id (RIASEC/CHASIDE/TIPOV). `tutor-prompt.test.ts` pins this: with a zero `scores` vector plus a CHASIDE `method` context, the prompt contains the real CHASIDE dimensions and interpretation but `not.toContain("R (Realista): 0%")` and `not.toContain("Código RIASEC Dominante")`.

### CHASIDE Interés vs. Aptitud split, persisted and read defensively

`scoreChaside` returns `raw: { interes, aptitud, topInteres, topAptitud }` where `interes`/`aptitud` are `Record<ChasideArea, number>` counts in the documented 0–10 and 0–4 ranges. The sessions API carries this through with `raw: result.raw ?? null`. `parseMethodScores` accepts `raw` only when it is a non-null, non-array object and otherwise stores `null`, keeping old rows and malformed values safe.

The results page's `ChasideInteresAptitud` re-validates via `parseChasideCounts` (both `interes` and `aptitud` must be numeric maps) and renders two separate bars per area, dividing by `CHASIDE_INTERES_MAX = 10` and `CHASIDE_APTITUD_MAX = 4`. When counts are absent it shows a Spanish notice rather than repeating combined bars — the exact misleading behavior v1 flagged. The data contract is locked by the new `chaside-engine.test.ts` case, which asserts the count values and that they survive `JSON.parse(JSON.stringify(raw))`, matching the JSONB persistence path.

### Regression checks

`git diff main` shows `web/lib/riasec/engine.ts`, `web/tests/engine.test.ts`, and `web/data/seed.ts` unmodified. `authorizeSessionRead` runs at the top of the session block in the chat route, before the `methodId` branch, unchanged from v1; the report/results paths retain their pre-branch authorization. `getMethod` is a synchronous registry lookup with no import-time DB or network, so the no-env `next build` invariant holds, consistent with the green typecheck/lint/build and 115/115 test run.
