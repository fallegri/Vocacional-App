# Selectable vocational test methods: pluggable registry with CHASIDE and TIPOV (v1)

A pluggable method registry (`web/lib/methods/`) lets a student — or a staff-assigned cohort — pick which vocational instrument to run. RIASEC stays the default and is wrapped by an adapter that delegates to the existing, byte-unchanged engine so its persistence (r/i/a/s/e/c columns), radar/careers/AI results view, and 20 tests are untouched. Two new fully-interactive instruments are added: CHASIDE (98 dichotomous items over 7 areas, Interés + Aptitud scored separately) and TIPOV (66 Likert-3 items over 13 dimensions). Persistence gains `method_id` + `method_scores` (JSONB) on sessions and `method_id` on cohorts via idempotent `ADD COLUMN IF NOT EXISTS` migrations, and the QR `/g/{code}` flow carries the cohort's assigned method into `/assessment`.

**Watch for:** the Tutor IA chat route injects an all-zero RIASEC profile and RIASEC career matches for CHASIDE/TIPOV sessions instead of their real `method_scores` (confirmed); the CHASIDE results "Interés vs. Aptitud" panel does not actually split interest from aptitude — it repeats the combined per-area bars (confirmed). Neither blocks correctness of scoring or authorization.

**Verdict**: NEEDS_CHANGES

## High-level view

The registry is the single source of truth: each method exposes `dimensions`, `questions`, a `scale`, and a pure `score()` returning a uniform `MethodResult`. RIASEC is adapted rather than rewritten, and `normalizeMethodId` funnels any unknown/absent identifier back to RIASEC everywhere (API, cohort read, QR redirect), which keeps old rows and malformed input safe.

Scoring is faithful to the source docs. CHASIDE counts "Sí" per area separately for Interés (max 10) and Aptitud (max 4), picks the top two per dimension, and its item bank is exactly 70 + 28 = 98. TIPOV sums Likert-3 raw values per dimension with a 0–100 normalization, 66 items across 13 dimensions. Both item banks are declared original faithful adaptations, consistent with the docs which only define structure/scoring plus one seed item per dimension.

Persistence is additive and idempotent. Non-RIASEC rows write neutral zeros to r/i/a/s/e/c and store the real per-dimension result in `method_scores` JSONB, parsed back defensively. The no-env build invariant holds — all queries are lazy and the new modules import no DB/network at module load.

Authorization is method-agnostic: `authorizeSessionRead` gates on ownership/staff by email regardless of method, and session creation fixes the owner to the authenticated student's email (non-forgeable). The results page and AI-report route both route non-RIASEC sessions through method-aware branches. The Tutor IA chat route is the exception — it still builds RIASEC-only context for every session.

### Registry as the single contract, RIASEC by adaptation

RIASEC is wrapped, not touched: `riasec-adapter.ts` imports `calculateScores`/`getDominantCode`/`getDominantProfileDescription` and the `QUESTIONS` seed unchanged, and stashes the original `PsychometricScores` in `result.raw.scores` so the r/i/a/s/e/c persistence path is identical to before. `method-registry.test.ts` pins this by asserting the adapter reproduces `calculateScores` values to 10 decimals and that `raw.scores` deep-equals the engine output. The git diff confirms `web/lib/riasec/engine.ts`, `web/tests/engine.test.ts`, and `web/data/seed.ts` are unmodified; `web/lib/riasec/types.ts` gains only an optional `methodId?` on `CohortGroup`.

`normalizeMethodId` is the choke point for untrusted method identifiers — it uppercases and whitelists exactly RIASEC/CHASIDE/TIPOV, else returns RIASEC. It is applied on the API body, on cohort rows read from the DB, and on the QR redirect, so a stale/garbage `method_id` column or a forged `?method=` param degrades to the default rather than crashing a lookup.

### CHASIDE and TIPOV scoring fidelity

CHASIDE matches the doc's calificación: `countAffirmatives` counts only value-1 ("Sí") answers, keyed by the item's `category` into separate Interés/Aptitud maps, and `topTwoAreas` returns the two highest areas per dimension with canonical-order tie-breaking. The bank in `data.ts` is built as 7 blocks of 14 (10 Interés + 4 Aptitud) = 98, over exactly C,H,A,S,I,D,E — asserted directly by `chaside-engine.test.ts` (98 items, 10/4 per area, unique ids 1..98, "No" ignored, top-two selection, all-No neutral message). The normalized `value` blends Interés+Aptitud over 14 — a visualization choice the doc doesn't dictate — while `dominantCodes` derives from Interés only, matching the doc's profile rule.

TIPOV sums raw Likert values per dimension and normalizes `raw / (3 * itemCount) * 100`, matching the doc's "suma cruda por dimensión, mayor = más interés." The bank is 66 items across 13 dimensions (5 each, Tecnología 6) — the 6th Tecnología item is an explicit padding choice to reach the documented 66, which the doc supports only at the structural level, not by item. `tipov-engine.test.ts` covers raw sums, the normalization formula, top-3 selection with canonical tie-break, and both Likert extremes.

Both banks carry a header documenting that the source docs define structure/scoring and a single example item per dimension, so the wordings are original adaptations rather than the verbatim instruments. That is the right disclosure; a reviewer approving clinical use should still validate item wording against a licensed source.

### Persistence: additive columns, neutral RIASEC fields, defensive JSONB

`method_id TEXT NOT NULL DEFAULT 'RIASEC'` and `method_scores JSONB` are added both in the `CREATE TABLE` and via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`; adding a NOT NULL column with a DEFAULT backfills existing rows to RIASEC, so old sessions render through the RIASEC branch. Non-RIASEC inserts write `NEUTRAL_SCORES` (all zero) to r/i/a/s/e/c and put the real result in `method_scores` — the NOT NULL r..c constraints are satisfied without polluting RIASEC semantics. `parseMethodScores` accepts either a parsed object or a JSON string and returns null on any malformed shape, so a bad JSONB value degrades the results view to the "no scores available" state rather than throwing.

The no-env build invariant holds: `env -u DATABASE_URL -u AI_API_KEY next build` exits 0, and the new modules run no query at import — every read/write goes through the lazy `query()`/`withTransaction()`, and `listSessions`/`listCohorts` swallow DB errors to `[]`/seed.

### Authorization stays method-agnostic

`authorizeSessionRead` decides purely on `studentEmail` ownership vs. staff role and never inspects the method, so a STUDENT sees only their own sessions for CHASIDE/TIPOV exactly as for RIASEC. Both the results page and the AI-report route call it before branching on method, and the report route special-cases non-RIASEC to avoid emitting a zero-profile RIASEC report. Session creation fixes `ownerEmail` to the authenticated student's email and ignores client-supplied `studentEmail` for students (staff proctoring still honored) — non-forgeable ownership is preserved unchanged for the new methods.

The gap is the Tutor IA chat route. It runs `authorizeSessionRead` correctly, but when the session loads it always does:

```ts
const careerMatches = matchCareers(session.scores, CAREERS);
ctx.scores = session.scores;          // all zeros for CHASIDE/TIPOV
ctx.dominantCode = session.dominantCode;
ctx.topCareers = careerMatches;       // RIASEC careers from a zero vector
```

For a CHASIDE/TIPOV session this grounds the tutor on an all-zero RIASEC profile and RIASEC career matches while ignoring `session.methodScores`. Authorization isn't affected, but the conversation context is wrong for two of the three methods. The report route already shows the correct pattern (branch on `session.methodId !== "RIASEC"`); the chat route should follow it.

### Method selection, cohort assignment, and QR flow

`/assessment` builds serializable `MethodOption`s (no `score` fn shipped to the client) and preselects from the cohort's assigned method if present (locked, non-editable), else from `?method=` or default. `buildAssessmentRedirectPath` omits the `method` param when it's null or RIASEC, keeping RIASEC URLs byte-identical to before, and `/g/[code]` resolves the cohort's method server-side before redirecting. `qr.test.ts` covers the redirect path and RIASEC omission. Cohort creation is gated by `authorizeStaffWithRoles(["SUPER_ADMIN","TEST_ADMIN"])` and normalizes the method before insert.
