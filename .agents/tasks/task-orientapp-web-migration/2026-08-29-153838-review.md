# Android-to-web migration of OrientApp with RAG knowledge base and cohort QR codes (v1)

The native Android vocational app (Kotlin/Compose/Room) is re-implemented as a Next.js 15 App Router web app under `web/`, targeting Vercel + Neon Postgres. The RIASEC psychometric engine is ported verbatim from `PsychometricEngine.kt` into pure TypeScript; the student assessment flow, results radar, and careers explorer are rebuilt as server/client components; a server-side OpenAI-compatible AI advisor gains a pgvector-backed RAG knowledge base (books / research / articles) with cited retrieval; and cohort creation now emits a QR code linking to the group-scoped test form. AI keys and the DB connection string stay server-only, all DB/AI access is lazy and runtime-gated so `next build` passes with no env vars, and 39 Vitest tests plus typecheck/lint are green.

Watch for: mutation endpoints (`/api/knowledge`, cohort creation, AI-config save, session review) have **no authorization** of any kind — broader than the acknowledged "no OAuth" student stand-in (confirmed). Session persistence writes the session row and each response row without a transaction, so a mid-write failure leaves partial data behind a `201` (confirmed). The `neon()` HTTP client and the `sql` tagged-template helper in `lib/db.ts` are dead code — every caller uses the `Pool`-based `query()` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The psychometric math is a faithful line-for-line port: scoring, the speed-trap / straight-lining / mirror-pair heuristics, the 70/30 cosine+euclidean career match with the dominant-code 1.05 boost and 30–99 clamp, and the two-letter profile map all match the Kotlin source, with stable-sort semantics preserved via explicit index tiebreaks.

The RAG layer is correct where it counts: chunking is pure and overlap-bounded, embeddings are stored into `vector(1536)` via `$n::vector` casts, and retrieval uses pgvector cosine (`<=>`) with parameterized binding, an HNSW index, and citation metadata surfaced back into the prompt. Every RAG path degrades gracefully to `[]` (and the advisor falls back to a heuristic report) when there is no DB, no AI key, or a dimension mismatch. One edge remains: `embedTexts` trusts provider array order rather than the response `index` field.

The QR requirement is met end to end: creating a cohort yields a QR whose payload is `{base}/g/{CODE}`, and `/g/[code]` redirects into `/assessment?cohort=CODE`. The base URL is resolved from an explicit origin, then `NEXT_PUBLIC_APP_URL`, then a relative path — never hard-coded localhost.

Secrets handling is sound: the AI API key and `DATABASE_URL` are read only inside server code, `getAiConfigView` returns a `hasApiKey` boolean rather than the key, and all SQL is parameterized. The gap is authorization, not secrecy — the staff/mutation surface is completely open, and the AI key is persisted in `ai_config` in plaintext.

Build-time safety holds: DB and AI clients are lazily constructed on first query, and every route or page that touches them sets `runtime = "nodejs"` and `force-dynamic`, so a no-env production build never opens a connection.

The `lib/db.ts` rework left two coherent-but-redundant clients: the intended `Pool`-backed `query(text, params)` that all callers use, and an unused `neon()` HTTP client plus `sql` tagged template that no caller references — a maintenance trap where future code could pick the wrong path.

### Psychometric engine ported verbatim from PsychometricEngine.kt

Scoring shifts each answer by `score - 1`, clamps to `[0,4]`, scales against `4 * answeredCount`, and clamps to `[0,100]` exactly as the Kotlin does. The quality heuristics match on every threshold: speed trap at `avg < 1100ms && validTimes >= 10`, straight-lining at `repetitionRatio >= 0.75 && answers >= 15`, mirror-pair penalties of +20 (diff ≥ 3) / +10 (diff == 2) with a `[40,100]` consistency clamp, and the same `isValid` / reliability-level / warning ladder. Career matching reproduces the 70% cosine + 30% euclidean-proximity blend (distance normalized by `2.45`), the `primaryMatch` 1.05 boost capped at 99.5, the final `[30,99]` clamp, and the four match-level bands.

The one place Kotlin and JS semantics diverge is sorting: Kotlin's `sortedByDescending` is stable, so the port re-implements descending sort with an explicit original-index tiebreak in `scoresSortedDesc` and in `matchCareers`. That preserves the tie ordering the Android app produced, which matters for dominant-code derivation and for which career surfaces first among equal-affinity matches. The `getDominantProfileDescription` two-letter map is copied entry-for-entry including the Spanish text.

### RAG knowledge base: chunking, pgvector storage, and cited retrieval

Ingestion chunks content with a pure `chunkText` (default 1200 chars, 200 overlap, cut on paragraph/sentence/space boundaries within the last 30% of the window), embeds the chunks, and inserts them into `knowledge_chunks`. Vectors are written with `$4::vector` casts against the serialized `[a,b,c]` literal, matching the `vector(1536)` column; when embeddings are unavailable the chunks are stored with `NULL` embedding and a warning explains they won't be retrievable until re-indexed. A dimension guard rejects vectors whose length isn't 1536 before storing them as real embeddings.

Retrieval computes the query embedding, then runs a parameterized cosine search:

```sql
SELECT c.document_id, c.chunk_index, c.content,
       (c.embedding <=> $1::vector) AS distance,
       d.title, d.source_type, d.source_reference
  FROM knowledge_chunks c
  JOIN knowledge_documents d ON d.id = c.document_id
 WHERE c.embedding IS NOT NULL
 ORDER BY c.embedding <=> $1::vector
 LIMIT $2
```

The vector literal and limit are bound as parameters (no string interpolation), `k` is clamped to `[1,20]`, and results carry the document title + source reference so `buildKnowledgeContextBlock` renders a "Fuentes de conocimiento" block with an explicit instruction to cite title and reference. The schema backs this with an HNSW `vector_cosine_ops` index. Every failure mode — no `DATABASE_URL`, no embeddings, query error — returns `[]`, and the advisor route then falls back to the heuristic analysis, so a missing knowledge base never breaks report generation.

One correctness caveat sits in `embedTexts`: it maps the provider's `data` array by position and `filter`s out non-array entries, without sorting by the OpenAI `index` field. In the normal case the provider returns vectors in request order and this is fine, but a reordered or partially-returned batch would silently misalign embeddings to their chunks — and because ingestion embeds all chunks of a document in one call, a large document is exactly where a provider is most likely to split or reorder. Sorting by `index` and asserting a 1:1 count (the count check already exists) would make this robust.

### Cohort QR links to the group-scoped test form

Cohort creation persists the group, and the client renders a QR whose value is `buildCohortTestUrl(code, origin)` → `{base}/g/{CODE}`. The `/g/[code]` route uppercases/normalizes the code and redirects to `/assessment?cohort=CODE`, so scanning the QR lands the student directly on the test bound to that group. `resolveBaseUrl` prefers an explicit origin, then `NEXT_PUBLIC_APP_URL`, then falls back to a relative path — localhost is never hard-coded, satisfying the requirement for a configurable deploy URL.

### Secrets stay server-side; authorization is absent

The AI key and `DATABASE_URL` are only ever read inside route handlers, server actions, and server-only libs. `getAiConfigView` deliberately returns `hasApiKey: boolean` instead of the value, and `saveAiConfig` preserves the existing stored key when the form submits an empty field, so the plaintext key is never sent to the browser on read. All SQL is parameterized via `query(text, params)`; no user input is concatenated into SQL.

The real gap is that none of the mutating surfaces check who is calling. `POST /api/knowledge` will ingest a document for any anonymous caller; `createCohort`, `saveAiConfig`, and the session-review PATCH are equally open. This is wider than the documented "seed-user/role selector is a known non-auth stand-in" caveat, which covers student identity — here the staff/admin operations (editing the AI provider config, uploading knowledge, writing reviewer verdicts) have no gate at all. It should be called out explicitly and gated before any real deployment, since an open `saveAiConfig` also lets an anonymous caller repoint the AI provider. Separately, `ai_config.api_key` is stored in Postgres in plaintext; env-var configuration avoids putting the key at rest in the DB.

### Session persistence has no transaction boundary

`persistSession` issues one INSERT for the session followed by one INSERT per response, each as an independent `query()` against the pool. There's no `BEGIN/COMMIT`, so a failure partway through the response loop (connection drop, timeout) leaves a persisted session row with only some of its responses — yet the caller has already computed scores from the full in-memory set, and `/api/sessions` returns `201 { id }`. The stored session would then disagree with any later recomputation from `assessment_responses`. Wrapping the whole persist in a transaction makes the write all-or-nothing. Relatedly, `cohortCode` is stored as-sent with no existence check, so a fabricated or stale code is accepted silently.

### Test coverage

The 39 tests cover the engine (scoring, quality heuristics, career matching, dominant-code, profile map), the pure chunker, the endpoint URL builders, and the knowledge-context block formatting including citation text. Not tested: any DB-touching path (session persist/load, cohort create, retrieval SQL, ingestion), the embedding-order assumption in `embedTexts`, the `/g/[code]` redirect, and the AI route fallback behavior — understandable given no live Neon/OpenAI creds, but it means the pgvector query, the `::vector` binding, and the retrieval join have not executed against a real database and rest on inspection alone.
