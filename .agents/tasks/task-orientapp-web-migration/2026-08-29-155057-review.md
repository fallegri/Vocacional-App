# Review-fix pass: staff-auth guard, embedding ordering, session transaction, DB cleanup (v2)

Second-pass review of commit `b32fb78`, which addresses the six findings from the v1 NEEDS_CHANGES review. The fix adds a token-based staff-authorization barrier gating all four staff mutation paths, sorts embedding responses by the OpenAI `index` field with a strict 1:1 count guard, wraps session persistence in a single transaction via a new `withTransaction` helper, removes the dead `neon()`/`sql` DB clients, and documents the plaintext AI key at rest and the intentional open cohort enrollment. Verification is green: typecheck, lint, 48 Vitest tests (up from 39, with new `ai-client` and `staff-auth` suites), and `next build` with no env vars.

Watch for: the staff guard is a shared-secret bearer token compared server-side and forwarded from `sessionStorage` — adequate as the documented deploy barrier it claims to be, but it is not per-user auth and offers no rotation, revocation, or audit (confirmed, by design and documented). All prior blocking concerns are resolved and no regressions were introduced in the psychometric engine, RAG retrieval, or QR flow.

**Verdict**: APPROVED

## High-level view

`embedTexts` now maps each provider entry to its `index` (falling back to arrival position when absent), sorts ascending, extracts vectors, and rejects any response whose vector count doesn't equal the input count — closing the v1 misalignment window on reordered or partial batches.

The staff guard closes the open-mutation hole on the server, not just the UI. All four sensitive operations enforce authorization at the server boundary: the two route handlers (`POST /api/knowledge`, `PATCH /api/sessions/[id]/review`) call `authorizeStaffRequest` and return `401` before any work; the two server actions (`createCohort`, `saveAiConfig`) call `authorizeStaff(input.staffToken)` and return an error before touching the DB. The barrier is a single shared `STAFF_ACCESS_TOKEN` with a constant-time compare; when the env var is unset the app is explicitly in "demo mode" and mutations stay open so a no-env build and demo keep working. The demo fallback is bounded to exactly that env-var-absent case and documented in the README, `.env.example`, and the token-field UI. It remains a shared secret, not per-user auth — no identity, rotation, revocation, or audit.

`lib/db.ts` is now a single Pool-based module: the dead `neon()` HTTP client, `getClient()`, and `sql` tagged template are gone, and every caller uses `query()` or the new `withTransaction()`, which releases its client on every path.

`persistSession` runs the session INSERT and all response INSERTs inside one `withTransaction`, so a mid-loop failure rolls back the whole write rather than leaving a partial session behind a `201`.

The plaintext `ai_config.api_key` is documented in the README security section, the schema comment, and the AI settings UI, with `AI_API_KEY` env-var configuration recommended for production. Cohort-code validation on persist is documented as intentional open QR enrollment.

### Embedding order and count guard in embedTexts

`embedTexts` builds `{ embedding, index }` pairs where `index` is the provider's `index` field when it is a number and the arrival position otherwise, sorts ascending by `index`, then extracts the vectors. Because ordering keys off `index` rather than array position, a provider that returns embeddings out of request order — the exact failure mode most likely on the large single-call batches that ingestion issues — realigns correctly. The absent-index fallback preserves arrival order.

The count guard makes the failure explicit rather than silent: a length mismatch against `inputs.length` returns an error (`"...N vectores para M textos..."`) instead of associating embeddings with the wrong chunks. The `filter` that drops non-array/empty entries runs before the count comparison, so a response containing a malformed entry fails the 1:1 check and is rejected — the safe direction (fail rather than misalign). New tests in `ai-client.test.ts` exercise reordering, the absent-index path, and partial-batch rejection.

### Staff authorization enforced at the server boundary

The guard lives in `lib/auth/staff.ts` and is applied at each of the four mutation entry points, not only in the client. `authorizeStaff(presented)` reads `STAFF_ACCESS_TOKEN`, returns `{ ok: true }` when it is unset (demo), and otherwise requires a trimmed, constant-time match:

```
route handlers ──> authorizeStaffRequest(req) ─┐
                   (reads x-staff-token header) │──> authorizeStaff(token)
server actions ──> authorizeStaff(input.staffToken) ┘   ├─ no env token  -> ok (demo)
                                                        ├─ no token given -> 401 / error
                                                        └─ mismatch       -> 401 / error
```

`POST /api/knowledge` and `PATCH /api/sessions/[id]/review` check authorization before parsing or persisting; `createCohort` and `saveAiConfig` check before any DB access. The token is compared only on the server and never returned to the browser. The `safeEqual` helper short-circuits on length difference — a minor timing signal on token length, immaterial for a deploy barrier of this class but worth noting if this ever hardens into real auth.

The demo-mode fallback triggers only when `STAFF_ACCESS_TOKEN` is absent, which is what keeps the no-env `next build` and the local demo functional, and it is documented in the README (security section and env table), `.env.example`, and the `StaffTokenField` helper text. The residual limitation is inherent to a shared secret: no per-user identity, rotation, revocation, or audit — the README states this is a barrier until full OAuth/SSO, out of scope for the migration.

On the UI side, admin server pages pass `isStaffAuthEnabled()` (a runtime env read, safe because all three admin pages are `force-dynamic`) to render `StaffTokenField` only when a token is required; `useStaffToken` holds the value in `sessionStorage` (tab-scoped, never `localStorage`) and forwards it as the `staffToken` action arg or the `x-staff-token` header. Absent tokens omit the header/arg, which the server rejects when enforcement is on.

### db.ts consolidated to a single Pool path with transactions

The dead `neon()` HTTP client, `getClient()`, and `sql` tagged template flagged in v1 are removed; a grep confirms no remaining references. What remains is a lazily constructed `Pool` (connection string read only on first query, preserving no-env build safety), the parameterized `query(text, params)`, and `withTransaction(work)`. The transaction helper acquires a client, exposes a `tx(text, params)` bound to it, runs BEGIN → work → COMMIT, ROLLBACKs and re-throws on error (swallowing only a secondary rollback failure so the original error surfaces), and releases the client in `finally` on every path.

### persistSession is now all-or-nothing

`persistSession` wraps the session INSERT and the per-response INSERT loop in one `withTransaction`, closing the partial-write-behind-a-201 scenario from v1: any failure in the response loop rolls back the session row as well. `cohortCode` is still stored as-sent with no existence check, now with a code comment explaining this is intentional open QR enrollment — consistent with the `/g/{CODE}` flow where a student may complete a test before the cohort is seeded, and staff filter by cohort in the admin panel.

### Regression check: engine, RAG retrieval, QR

The refactor did not touch the psychometric engine, `retrieve.ts`, or `qr.ts`. Retrieval still guards on `DATABASE_URL`, embedding availability, and the `EMBEDDING_DIMENSION` match, binds the vector literal and limit as parameters, and returns `[]` on any failure so the advisor falls back to the heuristic report. QR building still resolves the base URL from explicit origin, then `NEXT_PUBLIC_APP_URL`, then a relative path, and `/g/[code]` redirects into the group-scoped assessment. Engine, knowledge, and QR suites remain green.

### Test coverage

Coverage grew from 39 to 48 tests. New: `ai-client.test.ts` (embedding reorder, absent-index fallback, partial-batch rejection, empty input) and `staff-auth.test.ts` (demo-mode allow-all, token-enforced reject/accept with trimming, header extraction via `authorizeStaffRequest`). Not tested, unchanged from v1 without live creds: any DB-touching path — so `withTransaction`'s BEGIN/COMMIT/ROLLBACK and the `persistSession` rollback have not executed against a real Postgres and rest on inspection, as do the pgvector query and `::vector` binding. The staff guard is verified only through unit tests of the guard function, not through the route handlers and server actions end to end.
