# Google OAuth with role-based authorization for the OrientApp web admin (v1)

Adds Auth.js v5 (Google provider, JWT sessions, no DB adapter) and rebuilds staff authorization around real session roles instead of the shared-token stopgap. Roles are resolved from the authenticated email (seed users → env allowlists, highest-privilege-wins → STUDENT default) and enforced server-side at the four staff mutation entry points plus the three admin pages. The design preserves a hard build invariant: no secret is read at module load, so `next build`, `tsc`, and the demo mode all work with zero env vars. The old `STAFF_ACCESS_TOKEN` survives only as a fallback for deployments that haven't turned on OAuth yet.

Watch for: role is baked into the JWT at first login and never re-resolved, so allowlist/role changes don't take effect until the user signs out and back in — this cuts both ways (privilege escalation lingers, revocation lags) (confirmed).

**Verdict**: APPROVED

## High-level view

Authorization now has two mutually exclusive modes gated by `isAuthConfigured()` (all three of `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AUTH_SECRET` present). When OAuth is configured, the session role is the *only* gate and the shared token is fully inert — even a correct token can't elevate a STUDENT. When OAuth is not configured, behavior falls back to the prior world: token-enforced if `STAFF_ACCESS_TOKEN` is set, demo-open if not. The two modes never overlap, which is what keeps the demo and the build working without secrets.

Role resolution is a pure function of the email: exact match against seed `DEFAULT_USERS` wins first, then the `ADMIN_EMAILS` / `TEST_ADMIN_EMAILS` / `REPORT_REVIEWER_EMAILS` allowlists with highest-privilege-wins, else STUDENT. It reads env at call time, so it's build-safe.

The role is resolved once in the Auth.js `jwt` callback at sign-in and stored in the token; every later request reads it from the JWT without re-resolving. That's the one behavioral sharp edge: changing an allowlist or promoting a user has no effect until their next login.

The API surface: the four mutations (`createCohort`, `saveAiConfig`, `POST /api/knowledge`, `PATCH /api/sessions/[id]/review`) each declare the roles that may run them, the three admin pages render an `AccessRestricted` fallback instead of the tool when the guard fails, and sign-in/out run through server actions so no NextAuth client bundle is needed. First login best-effort links the user into `app_users` only when `DATABASE_URL` is set.

### Two-mode gate keyed on `isAuthConfigured()`

`isStaffAuthEnabled()` returns `false` the moment OAuth is configured, so `authorizeByToken` is unreachable in that mode. `authorizeStaffWithRoles` branches on the same predicate: configured → require a session whose role is in `allowedRoles`; not configured → `authorizeByToken` (shared token if set, demo-open otherwise). The test suite pins the important asymmetry directly — with OAuth on, presenting the correct `STAFF_ACCESS_TOKEN` still fails for a STUDENT:

```ts
process.env.STAFF_ACCESS_TOKEN = "secreto";
currentUser = { email: "alumno@x.com", role: "STUDENT" };
const res = await authorizeStaffWithRoles(["SUPER_ADMIN"], "secreto");
expect(res.ok).toBe(false);
```

Fail-closed in the configured mode, deliberate fail-open (demo) only when no secrets exist — the property that preserves the build-without-env invariant.

### Role resolution and the JWT staleness edge

In the `jwt` callback the role is computed only when `user` is present (first sign-in) and then persisted on the token; the `else if (!token.role ...)` branch only backfills a missing role, it never recomputes. On every subsequent request the `session` callback copies `token.role` straight through. Consequence: promote someone by adding them to `ADMIN_EMAILS`, and nothing changes until they sign out and back in; likewise a demotion or removal from an allowlist keeps working until the JWT naturally expires. With the JWT strategy there's also no server-side session store to revoke against. Not a bypass, but an operational expectation worth documenting; if near-real-time role changes are ever needed the fix is to re-resolve in the `session` callback rather than trust the cached value. (confirmed)

### Enforcement points and the demo carve-out

The four mutations each name their allowed roles rather than sharing a blanket "staff" check: cohort creation and AI config require `SUPER_ADMIN | TEST_ADMIN`, knowledge ingest accepts any staff, and the reviewer verdict requires `REPORT_REVIEWER | SUPER_ADMIN`. The status code moved from 401 to 403 on the route handlers (authenticated-but-forbidden). The three admin pages run the guard server-side and return `AccessRestricted`; `AdminClient`'s `canManageCohorts` is only UI sugar on top of the server check. When `isAuthConfigured()` is false the pages render as before, matching the mutation fallback.

Only mutations and the admin pages are gated. `GET /api/knowledge` and the session reads stay open regardless of mode, so data is reachable through the read API even when the admin UI is locked behind a login. If that's intended (public catalog, demo data) it's fine; flagging it because it's the kind of asymmetry that's easy to miss. (possible)

### First-login user linking

`linkOrCreateUser` runs in the Auth.js `signIn` event, does nothing unless `DATABASE_URL` is set, and swallows all DB errors so a link failure never blocks login. It inserts with a synthetic id `google:<email>` and `ON CONFLICT (id) DO NOTHING`; the SELECT-by-lowercased-email short-circuits existing rows, so seed users (ids like `user_super_admin`) are matched by email and not duplicated. One theoretical gap: `app_users.email` has no unique constraint, so two rows for the same email created through different id paths wouldn't be caught — nothing in this diff creates that path, and the id conflict clause covers concurrent first-logins. The row isn't updated on later logins, so its `role` can drift from the JWT per the staleness note above (expected for best-effort linking).

### Build invariant and deprecation hygiene

Verified locally with `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AUTH_SECRET`, `DATABASE_URL`, `STAFF_ACCESS_TOKEN` all unset: `typecheck`, `lint`, `test --run` (68 green), and `build` pass. The lazy config function on `NextAuth(() => ...)` and the lazy DB pool are what make this hold. The deprecated `StaffTokenField` / `useStaffToken` are unwired from all three admin clients and carry `@deprecated` notes pointing at the OAuth model.
