# Atomic source_key on insert closes the ingestion idempotency window (v2 review)

The follow-up commit `f11ab45` addresses the v1 idempotency finding. `IngestDocumentInput` now carries an optional `sourceKey`, and `ingestDocument()` persists it in the same `INSERT INTO knowledge_documents (…, source_key) VALUES (…, $6)` that creates the row — so the document is born already keyed rather than keyed by a separate follow-up `UPDATE`. The ingestion script passes `sourceKey: descriptor.slug` and drops the post-insert `UPDATE`, keeping the defensive `DELETE … WHERE source_key = $1` before each insert. The remaining v1 item (untested `splitSqlStatements`) was deliberately deferred as out of scope.

Watch for: nothing blocking. The v1 duplicate window is closed **[confirmed]**; the change is backward compatible for the admin upload path and existing NULL rows **[confirmed]**; the two engines, results dual panel, registry, and no-env build are untouched by this commit and remain green (typecheck clean, 155 tests pass) **[confirmed]**.

**Verdict**: APPROVED

## High-level view

The v1 gap was a two-step write: the row was inserted unkeyed and keyed afterward, so a crash or `!ok` return between the two steps left a `source_key = NULL` row that the next run's delete-by-key could not reclaim. The fix folds the key into the creating `INSERT`, so any row a partial run leaves behind is already keyed and the next run's `DELETE FROM knowledge_documents WHERE source_key = $1` removes it before re-inserting. That closes both the mid-ingest-crash and the failed-document-leftover variants the v1 review flagged.

The `sourceKey` field is optional and normalizes empty/whitespace to `NULL`, so the sole other caller (`app/api/knowledge/route.ts`, admin upload) keeps producing unkeyed rows exactly as before, and the schema column stays nullable with the multi-NULL-tolerant unique index — pre-existing NULL rows are unaffected.

Nothing else changed in `f11ab45`: CIP-R, Magdalena, the generalized results panel, registry/types, and Spanish copy are byte-identical to the v1-reviewed state, and the no-env build invariant is intact.

Deferring the `splitSqlStatements` unit test is reasonable — it is a private helper duplicated across the out-of-scope `seed.ts` and the ingest script, both of which `main()` at import, so testing it would pull the out-of-scope seed path into the change.

### The idempotency window is actually closed

The v1 fragility was that `ingestDocument()` created the row with no key and the script keyed it with a trailing `UPDATE`, so a failure in between — or an `ingestDocument` returning `!ok` after the row and some chunks were written — left an unkeyed row that `DELETE … WHERE source_key = $1` would never match, yielding a duplicate on the next run.

The row is now created keyed in one statement:

```ts
const sourceKey = (input.sourceKey ?? "").trim() || null;
const docRows = await query(
  `INSERT INTO knowledge_documents (title, source_type, source_reference, created_at, created_by, source_key)
   VALUES ($1, $2, $3, $4, $5, $6)
   RETURNING id`,
  [title, sourceType, sourceReference, now, input.createdBy ?? null, sourceKey]
);
```

The script's per-file loop deletes by `source_key` first, then calls `ingestDocument({ …, sourceKey: descriptor.slug })`, and the trailing `UPDATE` is gone. Any row a failed run leaves behind — whether the process dies after the document insert, during a per-chunk insert, or `ingestDocument` returns `!ok` and the loop `continue`s — now carries the slug, so the next run's delete-by-key reclaims it (with `ON DELETE CASCADE` clearing its chunks) before re-inserting. Both v1 variants are covered. **[confirmed]**

A single transaction around delete+insert+chunks would be strictly more atomic — it would also prevent a torn read by a concurrent query mid-run — but the ingest script is a single-writer CLI, so keying-on-insert is sufficient to close the re-run duplicate window that v1 identified. The code comments state this trade-off explicitly. **[confirmed]**

### Backward compatibility of the sourceKey addition

`sourceKey` is optional on `IngestDocumentInput` and coerced with `(input.sourceKey ?? "").trim() || null`, so both an absent field and an empty/whitespace string land as `NULL`. The only other caller, the admin upload route, does not pass it and therefore continues to create unkeyed documents — deduplication remains a script-only concern, which is the intended design. The schema keeps `source_key` nullable with `CREATE UNIQUE INDEX IF NOT EXISTS uq_knowledge_documents_source_key`, and since Postgres permits multiple NULLs under a unique index, pre-existing unkeyed rows and future admin uploads coexist without collisions. The no-env build path never constructs an `ingestDocument` call, so the added parameter cannot affect it. **[confirmed]**

### No regression to the rest of the change

`f11ab45` touches only `web/lib/knowledge/ingest.ts` and `web/scripts/ingest-knowledge.ts` (plus comments). The CIP-R engine (114 items / 15 scales, 2/1/0 mapping), the Magdalena engine (120 items / 10 fields, 0–4, per-field max 24, documented bands), the generalized `InteresAptitudPanel` (CHASIDE 10/4, Magdalena 24/24), the registry/types, and the Spanish copy are unchanged from the v1-reviewed state. Typecheck is clean and the full suite runs 155 passing across 14 files. **[confirmed]**
