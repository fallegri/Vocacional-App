# Idempotent RAG ingestion script + CIP-R and Magdalena Contreras interactive methods (v1 review)

Three commits deliver two approved follow-ups. The first adds a repeatable knowledge-ingestion script (`web/scripts/ingest-knowledge.ts`) that applies `schema.sql` statement-by-statement and re-ingests the `skills/knowledge/*.md` docs through the existing `ingestDocument()` pipeline, deduplicating on a new nullable `source_key` column. The other two add two fully self-scored methods to the existing pluggable registry: CIP-R (114 items / 15 interest scales, Agrado/Indiferencia/Desagrado mapped 2/1/0) and Test Magdalena Contreras (dual Interés+Aptitud, 120 items across 10 fields, 0–4 scale, per-field max 24 with the documented interpretation bands). The registry, types, admin cohort options, and the results dual panel were extended, not re-architected, and the generic session/results/AI paths absorb both methods unchanged.

Watch for: (1) **[likely]** the ingestion script's idempotency is happy-path only — it inserts the document with `source_key = NULL` and sets the key in a separate follow-up `UPDATE`, so a crash or mid-ingest failure between the two leaves an unkeyed row that the next run's delete-by-key won't clean up, producing a duplicate. Scoring math, band cut points, item counts, the no-env build invariant, Spanish copy, and test meaningfulness all check out.

**Verdict**: APPROVED

## High-level view

The two engines are faithful to their source docs. CIP-R sums a 2/1/0 mapping per scale and normalizes against `2 × itemCount`; the doc defines A/I/D qualitatively without numeric weights, so the mapping is the implementation's own faithful choice and is disclosed in both the engine header and the data-file comment. Magdalena sums Interés and Aptitud separately per field (max 24 each) and maps each total to the documented bands, correctly using the distinct Aptitud labels (Falta de Práctica / Aptitudes Comunes / Aptitudes Normales / Aptitudes Desarrolladas) rather than reusing the Interés labels. Both item banks are original faithful adaptations, disclosed as such in code and README, with structure matching the docs exactly (114 = 9×8 + 6×7; 120 = 10 fields × 6 × 2).

The registry extension follows the established one-folder-per-method contract: a new `LIKERT_0_4` scale kind, both methods registered, and `normalizeMethodId` widened to map `cipr`/`magdalena` and fall back to RIASEC for anything unknown. The generic session-scoring path persists `result.raw` verbatim, so Magdalena's per-field totals and bands survive to the results view without any special-casing in the API.

The results dual panel was generalized from CHASIDE-only to a shared `InteresAptitudPanel` driven by `hasDualPanel`, with per-method maxima (CHASIDE 10/4, Magdalena 24/24) and band suffixes rendered only when present. CHASIDE's `raw` carries no bands, so its rendering is unchanged, and old rows without raw totals still degrade to an advisory notice.

The ingestion script honors the no-env invariant: it guards on `DATABASE_URL` and exits with a Spanish message before touching the DB or network, reuses the lazy DB client, and skips the PDF by design. Its weak point is idempotency under partial failure, described below.

<summary>Issues (2)</summary>

1. **Ingestion idempotency under partial failure** — the document is inserted with `source_key = NULL` and keyed by a later `UPDATE`; a crash or `ingestDocument` failure between insert and update (or mid-chunk) leaves an unkeyed row that the next run's `DELETE ... WHERE source_key = $1` cannot remove, causing a duplicate. Consider having `ingestDocument` accept and persist `source_key` in the initial `INSERT` (single statement), or wrap delete+insert+key in one transaction.
2. **Failed-document rows are not rolled back** — when `ingestDocument` returns `!ok` after the row was created, the script logs a warning and continues, but a partially-inserted document/chunks set can remain; on re-run it is only cleaned if the key was set. Same fix as above resolves it.

### CIP-R scoring fidelity and the A/I/D→2/1/0 mapping

The source doc specifies the single-choice Agrado/Indiferencia/Desagrado response format and the raw-sum-per-scale rule, but assigns no numeric weights to the three options. The engine picks Agrado=2 / Indiferencia=1 / Desagrado=0 and normalizes `raw / (2 × itemCount) × 100` — monotonic with attraction, minimum at Desagrado — disclosed in the engine header and `data.ts`, asserted in `cipr-engine.test.ts`, with the registry scale options ordered 2→1→0 to match. **[confirmed]**

The 114-item distribution (first 9 scales × 8 + last 6 scales × 7) and unique IDs 1..114 are asserted directly. Top-3 dominant selection uses raw sum with a canonical-order tie-break, verified where two scales tie at 16 and the earlier canonical scale wins. All-Desagrado returns the neutral Spanish "No se registraron…" message rather than a spurious dominant profile. **[confirmed]**

### Magdalena dual scoring and band cut points

`sumByField` splits Interés and Aptitud into separate per-field totals (6 × 4 = 24 max each); `scoreMagdalena` normalizes the combined dimension bar against 48. Dominant codes are the top-3 by Interés. The band functions implement the documented cut points exactly:

```
Interés:  0–6 Falta de Motivación · 7–12 Intereses Comunes ·
          13–18 Intereses Subprofesionales · 19–24 Intereses Profesionales
Aptitud:  0–6 Falta de Práctica · 7–12 Aptitudes Comunes ·
          13–18 Aptitudes Normales · 19–24 Aptitudes Desarrolladas
```

The Aptitud bands correctly use their own labels rather than mirroring the Interés labels — a place where a careless port would have gone wrong. `magdalena-engine.test.ts` pins every boundary (0, 6, 7, 12, 13, 18, 19, 24) for both dimensions. The interpretation surfaces an Interés-vs-Aptitud mismatch (interest ≥13 with aptitude ≤12) in the dominant field, matching the doc's distortion-detection purpose; a test drives Cálculo interest=24 / aptitude=6 and asserts the mismatch text ("Falta de Práctica"). **[confirmed]**

### Ingestion idempotency gap under partial failure

The happy-path dedup is sound: `source_key` is the file slug, `DELETE FROM knowledge_documents WHERE source_key = $1` runs before re-insert, `ON DELETE CASCADE` clears old chunks, and the unique index (allowing multiple NULLs) backs it.

The fragility is the two-step write. `ingestDocument()` inserts the row with no `source_key`, then the script sets it afterward:

```ts
const result = await ingestDocument({ title, sourceType, sourceReference, content, createdBy });
// ... row now exists with source_key = NULL ...
await query(`UPDATE knowledge_documents SET source_key = $1 WHERE id = $2`, [descriptor.slug, result.documentId]);
```

If the process dies between the insert inside `ingestDocument` and this `UPDATE` — or if `ingestDocument` fails partway through its per-chunk inserts and returns `!ok` (the script logs and continues) — a document row (possibly with some chunks) persists with `source_key = NULL`. The next run's delete-by-key does not match NULL rows, so the re-insert produces a second copy, defeating idempotency. There is no transaction wrapping delete+insert+key. Passing `source_key` into `ingestDocument`'s initial `INSERT` (single-statement, atomic) or wrapping the three operations in one transaction closes both this window and the failed-document-leftover case. **[likely]**

### No-env build invariant and degradation

The script guards `process.env.DATABASE_URL` at the top of `main()` and exits(1) with a Spanish message before reading files, applying schema, or hitting the network; it reuses the lazy `query` client, so `next build` never triggers it. `schema.sql` stays fully idempotent (`IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`, plus the new `source_key` column and unique index). When AI is unconfigured, chunks are stored with NULL embeddings and the script prints a Spanish warning with reindex instructions — the intended degradation. Engines and data modules are pure (arrays built at import, no env reads, no I/O), safe to import during build. **[confirmed]**

### Registry and generic-path integration

`types.ts` widens `MethodId` and adds `LIKERT_0_4`; `registry.ts` registers both methods and extends `normalizeMethodId` (case-insensitive, RIASEC fallback), all asserted in `method-registry.test.ts` including the 114/120 counts. The generic session path stores `result.raw` verbatim, so Magdalena's `interes`/`aptitud`/`interesBands`/`aptitudBands`/`fieldMax` reach the results view unchanged; the panel keys on `hasDualPanel` (CHASIDE or MAGDALENA) with per-method maxima and band suffixes rendered only when the maps are present. CHASIDE carries no bands, so its output is unchanged, and pre-existing rows lacking raw totals fall back to the advisory notice. AdminClient's `METHOD_OPTIONS` gains both entries. **[confirmed]**

### Test coverage

The three suites are real, not stubs: 13 CIP-R cases (bank shape, mapping, per-scale sums, normalization, tie-break, empty/all-zero, JSON round-trip), 14 Magdalena cases (bank shape, every band boundary, dual sums, normalization against 48, dominant-by-Interés, mismatch detection, round-trip), 13 knowledge-source cases (slug derivation with diacritics, H1/fallback titles, RESEARCH type, references for CIP-R/Magdalena, unique slugs across all 7 md files), plus the registry suite updated for both methods. Ran locally: 45 passed.

Not tested: the ingestion script's runtime behavior (DB writes, dedup, partial-failure recovery) has no coverage — expected without live Neon/OpenAI credentials, and its pure helper and schema idempotency are covered indirectly. The `splitSqlStatements` SQL splitter hand-rolls quote/comment handling and is untested; it works for the current `schema.sql` but a targeted unit test would be cheap insurance if the schema later grows more complex string literals. **[possible]**
