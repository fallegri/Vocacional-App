# QR group flow, individual auth gate, Resend removal, and Reportes tab (v2)

This change removes Resend email entirely, wires up immediate account verification on registration, adds an authentication gate for individual (non-QR) assessment access, and adds a Reportes tab in the admin panel with general and per-group reporting plus CSV export. The fix commit (07642de) addressed all three issues raised in v1: the success screen no longer mentions email or Resend, the blank line before `handleRoleChange` was added, and a staleness banner ("Ultima actualización") now appears at the top of the Reportes tab. All verification checks pass (tsc, lint, tests, build).

Watch for: **(confirmed)** `loginAction` still carries a dead `unverified` branch that tells the user to "check their email for a confirmation link" — no verification email is ever sent. **(confirmed)** `app/verify/page.tsx` is a live public route that consumes `verifyEmailAction`; since no tokens are created in the new flow, any user who lands there gets "invalid or expired" with no useful recovery path. **(confirmed)** the `resent:true` path in `registerAction` returns `ok:true` with an `error` field — `RegisterForm` renders success on `result?.ok` without checking `resent`, so the conflict-resolution message is silently discarded.

**Verdict**: NEEDS_CHANGES

---

## High-level view

All three v1 concerns are resolved.

`loginAction` retains a dead branch for `cuenta_no_verificada` that directs users to check their email for a link that will never arrive. Pre-existing unverified accounts (created before this deployment) or any state where the credentials adapter still checks `emailVerifiedAt` can still trigger this path.

`app/verify/page.tsx` is a publicly reachable route that calls `verifyEmailAction`. No token is created anywhere in the current flow, so the route permanently returns an error. The page copy and the "register again" recovery path are both wrong for the new model.

`RegisterForm` branches on `result?.ok` only. `registerAction` returns `{ ok: true, resent: true, error: "...Inicia sesión directamente." }` for conflict resolution — the `error` field is never rendered in the success branch, and the `resent` flag is never checked.

### Dead unverified branch in loginAction

`loginAction` catches an `AuthError` whose `cause.err.message` is `"cuenta_no_verificada"` and returns `{ ok: false, unverified: true, error: "Tu cuenta aún no ha sido verificada. Revisa tu correo…" }`. `LoginForm` renders this with a paragraph linking to `/register?resend=1`.

Since `markEmailVerified` is now called at every registration path (both new user and the `resent` conflict path), no account created after this deployment should have `emailVerifiedAt = null`. But accounts created before this deployment, or rows with direct DB state, could still reach this branch. If the credentials adapter still checks `emailVerifiedAt` and throws `cuenta_no_verificada`, those users receive instructions to check an inbox for a link that will never be sent.

### `/verify` as a publicly-accessible dead end

`verifyEmailAction` calls `consumeVerificationToken`, which queries `verification_tokens`. No token is inserted anywhere in the current flow, so `consumeVerificationToken` returns `null` for any input, and every visit to `/verify?token=...` produces an error screen. The copy ("usa el enlace que recibiste en tu correo") is permanently wrong, and the recovery path ("Registrarse nuevamente") creates a silently-verified account without explaining the state change to the user.

</details>
