# Credentials auth, deterministic engines, and group management

Three features land together: (A) removal of the entire RAG/AI stack, (B) replacement of Google OAuth with email+password credentials auth using Auth.js v5 JWT sessions, bcrypt, and email verification via Resend, and (C) cohort-to-group rename with per-group method assignment, user-role management panel, and results-email delivery. The five deterministic method engines (RIASEC, CHASIDE, TIPOV, CIP-R, Magdalena) are the sole analysis mechanism — `method_id` and `method_scores (JSONB)` columns carry the result for non-RIASEC sessions. All three features verify clean: 165 Vitest tests green, tsc clean, lint 0, no-env build passes.

**Watch for:**
- `setUserRole` has no self-demotion guard: a SUPER_ADMIN can demote their own account to STUDENT with no confirmation or lockout mechanism (confirmed).
- `createUser` computes `now = Date.now()` and passes it as `$6` in the params array, but the INSERT SQL hardcodes `email_verified_at = NULL` and has only 5 positional placeholders — `now` is a dead variable (confirmed).
- No password-reset flow exists. A user who loses their password has no self-service recovery path; re-registering the same email hits `ON CONFLICT DO NOTHING` and returns "Ya existe una cuenta" (confirmed).
- `sendVerificationEmail` falls back to `http://localhost:3000` when `NEXT_PUBLIC_APP_URL` is unset — production deployments without that variable send verification emails with unreachable links (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

Auth.js is configured with a lazy factory that registers the Credentials provider only when `AUTH_SECRET` is present, preserving the no-env build invariant. The JWT carries `{ email, role }` stamped at login; role is never re-read from the database on subsequent requests, so a `setUserRole` change takes effect only after the user's next login.

The registration→verification flow inserts an unverified user, dispatches a 24-hour UUID token via Resend, and marks the account verified when the token is consumed. Two gaps: there is no resend-token or password-reset endpoint, and `registerAction` blocks re-registration of an existing email even when unverified, leaving users with expired tokens stuck.

The `sessions` API route branches on `methodId`: RIASEC sessions go through the existing Holland path; all other methods validate against their own item bank, call `method.score()`, and store results in the `method_scores JSONB` column. `student_email` is pinned server-side for authenticated students — clients cannot spoof the owner field. Staff can still supply any `studentEmail` for proctored sessions.

`setUserRole` restricts execution to SUPER_ADMIN but has no guard against a SUPER_ADMIN targeting their own account. In a single-admin deployment, self-demotion locks out user management with no UI recovery path.

The email client never throws; verification emails and results emails are both best-effort. The `sendVerificationEmail` localhost fallback is the only silent production hazard in an otherwise well-contained error model.

1. **`createUser` dead `now` variable** — `now = Date.now()` is computed and passed as `$6` in the params array, but the INSERT SQL has only 5 placeholders (`$1`–`$5`) and hardcodes `email_verified_at = NULL`. The value is silently dropped by the driver. If a `created_at` timestamp is intended, add the column and placeholder; if not, remove `now`. (`web/lib/auth/users.ts` lines 67–76)

2. **SUPER_ADMIN self-demotion** — `setUserRole` allows a SUPER_ADMIN to target their own email and set `role = 'STUDENT'`. With a single admin account this locks out user management with no UI recovery path. Add a server-side check using `getCurrentUser()` to compare the caller's email against the target before applying the update.

3. **No password-reset flow** — A user who loses their password cannot recover: re-registering the same email returns "Ya existe una cuenta con ese correo" (`ON CONFLICT DO NOTHING`). Add a password-reset action or at minimum document the DB-side recovery procedure (`UPDATE app_users SET password_hash = … WHERE lower(email) = …`) in the README.

4. **Verification email localhost fallback** — `sendVerificationEmail` builds the verify URL using `NEXT_PUBLIC_APP_URL ?? 'http://localhost:3000'`. Any production deployment without `NEXT_PUBLIC_APP_URL` sends emails with localhost links that recipients cannot click. Mark the variable as required in `.env.example` or derive the base URL from the request `Host` header.

5. **No resend-verification endpoint** — After a 24-hour token expires, the verify page shows "Regístrate nuevamente", but `registerAction` blocks re-registration for the same email. The user has no self-service path. Allow `registerAction` to issue a fresh token for existing-but-unverified accounts, or add a `/resend-verification` action.

## Credentials provider wiring and role-staleness

`auth.ts` uses `NextAuth(() => { … })` so the factory runs per-request, not at module load. The JWT callback stamps `token.role` on first login; subsequent requests read it from the signed token without touching the database. A role change via `setUserRole` takes effect only after the user logs out and back in — the admin panel gives no indication of this, so an operator promoting a user may not understand why the change isn't reflected immediately.

## `createUser` dead variable — confirmed bug

```typescript
const now = Date.now();           // computed but unused

const rows = await query(
  `INSERT INTO app_users
     (id, email, display_name, role, password_hash, email_verified_at, auth_provider)
   VALUES ($1, $2, $3, $4, $5, NULL, 'EMAIL')`,
  [id, normalized, displayName.trim(), role, passwordHash, now]  // 6 params, 5 placeholders
);
```

`now` is the sixth element; the SQL has five `$N` slots. Most Postgres drivers silently ignore extra params, so the insert succeeds — `now` is just never stored anywhere.

## SUPER_ADMIN self-demotion

`authorizeStaffWithRoles(["SUPER_ADMIN"])` confirms the caller's role but doesn't expose their email. A check like:

```typescript
const caller = await getCurrentUser();
if (caller?.email === normalized) {
  return { ok: false, error: "No puedes cambiar tu propio rol." };
}
```

inserted before the UPDATE would close this.

## Token consumption race and missing resend path

`consumeVerificationToken` runs a SELECT then a separate UPDATE — a concurrent double-click races through the SELECT before either UPDATE commits. A single `UPDATE … WHERE consumed_at IS NULL RETURNING email` would be atomic and eliminate the window.

The verify page error path links to `/register` with the message "Regístrate nuevamente". `registerAction` returns the duplicate-email error for any account that exists — verified or not. Users with expired tokens hit a dead end.

## Resend email fallback URL

```typescript
const baseUrl = (process.env.NEXT_PUBLIC_APP_URL ?? "").trim() || "http://localhost:3000";
```

`NEXT_PUBLIC_APP_URL` is documented as optional in `.env.example`. The fallback is safe for local development but silently breaks production email flows. The results-email URL derivation in `POST /api/sessions` reads `x-forwarded-host` and `Host` headers as fallbacks — the same approach could be applied in `sendVerificationEmail` to avoid the localhost problem without requiring the env var.

## Test coverage

Covered: `authorize()` credential flow (5 cases), token create/consume lifecycle (expired, consumed, valid), email client skip/send/error modes, email message builders, password hash/verify, `setUserRole` authorization and DB calls, `authorizeSessionRead` (demo mode, anonymous, staff, owner, non-owner).

Not tested: `loginAction` → NEXT_REDIRECT path, concurrent token consumption race, `setUserRole` self-demotion, `registerAction` behavior for existing unverified accounts.
